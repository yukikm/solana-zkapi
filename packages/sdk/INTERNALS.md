# Solana zkAPI SDK

`./encoding` retains the integer and H2F primitives. `./layout2` encodes the exact layout-2 arguments. `./transport` builds v0 buffer operations and the optional single-transaction compact deposit, with no ALT, 1,000,000 CU requested and every serialized transaction limited to 1232 bytes. v1 and legacy-only wallet signing are not supported.

## Single-signature deposit

New deposits use `deposit_compact_v1` only when the authenticated manifest advertises `v0_inline_deposit_v1` and the independently installed `ManifestTrustPolicy.build.transactionFormats` includes both that capability and `v0_buffer`. The verified artifact bundle also checks the exact compact instruction discriminator, arguments and account roles in the pinned IDL. A fetched config cannot enable the capability by itself. Publish new IDL/program/build/distribution hashes together after isolated canary acceptance; do not replace the pins on an existing unresolved journal.

Compact encoding retains the same eleven public inputs, tree proof, verification key, account layout and USDC accounting. A normal self-funded deposit needs one wallet signature and one financial transaction. `beginDeposit` persists the private witness before tree proving; `advance` persists exact signed bytes before the initial send and activates funds only after exact finalized receipt and Note reconciliation. Separate token owner, Note rent payer and transaction fee payer are explicit roles; unused buffer roles are not persisted.

Compact operations use plaintext journal schema 2 within the existing encrypted envelope. Schema 1 buffer journals remain readable and keep their saved transport. Unknown sends, missing history, confirmed-only observations and blockhash expiry cannot authorize a new deposit, rebase or buffer fallback. Recovery observes the stored signature without automatically sending again. A verified finalized rejection permits explicit reproving with the same secret and amount; a new transaction requires a new signature. Withdrawal, escape, challenge and old deposits retain the buffer path.

The selected compact-deposit priority fee, including zero, is saved with the operation before proving. Unsigned snapshot refreshes, proof interruptions and explicit retries after finalized rejection retain that fee across restarts. Changing a client's default fee does not reprice an existing operation.

See [the implementation contract](../../docs/single-signature-deposit-design.md) and [local validation](../../docs/evidence/I10-single-deposit-implementation.md). Public deployment and real Phantom acceptance are separate from local tests.

The caller supplies the pinned program/pool profile, a verified host-prover output, finalized snapshot slot/sequence and explicit wallet roles. Encoding is not proof verification. `vaultAccounts` derives the canonical PDAs/ATAs and inserts the writable payer into unused Financial slots. Uploader, instruction payer, token owner, buffer rent payer and transaction fee payer can all differ.

1. `encodeLayout2Args` accepts the real host prover's public/proof fields and canonical protocol fields.
2. `buildUploadPlan` returns create/append/seal/execute steps. Append sizes are calculated from actual v0 serialization with the supplied signers. `closePayload` creates the cancellation/expired-recovery instruction; `finalizeEscape` creates the inline no-proof instruction.
3. `prepareAttempt` snapshots the plan, instruction and blockhash before awaiting wallets, verifies that the step matches the plan, collects explicit v0 wallet signatures, verifies every Ed25519 signature and preserves the message and earlier signatures. Wallet-returned transactions are copied before verification; changes to caller or wallet objects during a prompt cannot change the returned transaction or its recovery journal. An atomic durable `Journal.save` must complete before the signed bytes can be sent. The record includes payload/digest, buffer/nonce, operation, pool/accounts, expected root/ID, snapshot, blockhash/last-valid height and signature. Supply an encrypted durable implementation; an in-memory callback is suitable only for tests. I08 owns storage encryption and the user note journal.
4. `recoverAttempt(record, connectionTransport(connection), true)` snapshots the journal record, then reads historical signature status and a finalized transaction. A finalized receipt must match the signed message. An unresolved live attempt can resend the identical validated signed bytes, even if the caller changes its record during an RPC wait. RPC failure, confirmed-only results and missing receipts retain an unresolved result. Do not start another financial attempt while this one is unresolved.
5. After finalized blockheight exceeds expiry, `refreshExpiredUpload` can reconcile monotonic upload progress using `fetchFinalizedBuffer` and sign a fresh append/seal only if it is still required. It can return the next unsent step after an acknowledged prefix. Missing accounts never mean execute succeeded. Execute, finalize and close require finalized transaction/history reconciliation before any replacement attempt; expiration alone does not establish non-inclusion. This conservative stop includes history-pruned RPCs and uncertain buffer generations.
6. A finalized StaleRoot/StaleNoteId/InvalidExpiry error sets `needsNewProof`. Fetch current state/path and create a new proof/digest/buffer. Preserve clearance/nullifier state. Challenge keeps the historical request proof; close/escape require a new withdrawal proof for the current root. Close the old buffer to recover rent. Successful execute already closes it.

`prepareFinalizationAttempt` / `recoverFinalizationAttempt` provide the same durable signature recovery for standalone finalize, binding the note ID, pool, all accounts and snapshot without requiring a proof. Permissionless expired close uses `closePayload(plan, closer)` and the normal attempt journal records the exact closer. Both retain unresolved status after expired blockhashes when finalized history is unavailable; neither infers success from an absent account. `signV0` itself performs no RPC, provider call or implicit wallet/network selection.

## Verification

Run `npm run typecheck` and `npm test` with the repository's pinned Node/npm versions. Tests use real Ed25519 signing and serialized transactions. Simulated RPC failures and injected `Connection` JSON-RPC responses test transport recovery; they do not constitute a live wallet, public RPC, or provider acceptance gate. `test/sbf-transactions.ts` feeds the same SDK-generated transactions and checked-in real proof fixtures into the actual Vault SBF harness.

Dependencies are exact-pinned in this package and the root lockfile. The v0 API follows the [Solana transaction documentation](https://solana.com/developers/cookbook/transactions/versions) and [web3.js 1.98.4 release](https://github.com/solana-foundation/solana-web3.js/releases/tag/v1.98.4). The tested dependency baseline has npm moderate advisories inherited through `jayson` (`stream-json`, `uuid`). This transport imports web3's browser JSON-RPC client, which uses `JSON.parse` and `uuid.v4`; the reported stream filtering and UUID v3/v5/v6 buffer APIs are not called on this path. This is a reachability observation, not a clean audit or a production release approval; resolve or formally review the dependency chain before release.

## I08 trust, journal and control client

The I04 transaction transport remains the wallet execution layer. I08 adds trust verification, encrypted storage, control recovery and the proving/wallet composition described below. `apps/clientd/runtime.ts` uses the same SDK journal and clients for the Go daemon.

1. Authenticate the raw manifest with `trust.verifyManifest` using an independently installed distribution signature key or manifest hash, expected deployment and ADR-0002 build pins. `verifiedClientBundle` then snapshots and checks the actual finalized PoolConfig, genesis and all artifact bytes, returning `{ context, artifacts }`. Pass `context` to the control client and the returned, detached `artifacts` PK/VK bytes to the existing native prover; the original mutable input buffers are not authenticated outputs. `verifiedClientContext` remains available for callers that only need the context. A manifest fetched from the control server cannot supply its own trust root.
2. Create an `EncryptedJournal<NoteJournal>` with `validateNoteJournal` and a caller-supplied nonextractable AES-256-GCM key. Use `IndexedDbJournalStore` with Web Locks in browsers or `NativeJournalStore` on Node. Import only a separately verified finalized note; constructing a journal is not a deposit finality check.
3. Select direct/proxy explicitly. `quote` checks the signed quote and pinned tariff before proving. Generate credentials with `createCredentials`, and create the RP with the existing local prover. `prepare` verifies the actual RP, frozen quote/tariff, secrets and private commitment through `SessionVerifier`, then saves the exact authorization/proof/token before `submit` can send it.
4. `submit` persists `send_unknown` first. Recovery uses exactly the saved authorization and credentials. `close` on an unknown create durably retains close intent and repeats only that saved authorization until acknowledged, then closes the session; a newly returned direct key is withheld. A never-sent expired quote can be discarded with explicit `cancelUnsent`; a possibly sent one cannot. A direct session without its first-delivered key is closed and recovered. Configure `directProviderBases` independently; a mismatched base is never used and causes close. For `direct_oa`, also install `oaVerifier: { base: 'https://verifier.example', stationId: 'trusted-station' }` independently of control responses. The shared client checks the first-delivery `provider_key_verification`, then POSTs the exact key and signed evidence to the pinned `/submit_key` and requires `status: "verified"` before returning or saving the key. Verifier requests contain no control credentials, note identity, or prompts. There is no mode fallback.
5. For proxy inference, call `prepareOperation` with an explicit UUID and exact UTF-8 body, then `sendOperation` once. SSE is passed through as a `Response` stream. A timeout/409 retains the operation for `operationStatus`, never creates a new UUID or repeats inference. For admission failures before the server records an operation, explicitly call `reconcileAbsentOperations` after terminal settlement. It requires an authenticated missing-operation response and verifies every receipt and the signed successor before excluding the operation; an active session remains unresolved.
6. `close`/`recover` collect receipt pages and use the native verifier to check Ed25519 receipts, frozen integer prices, exact operation coverage and one session-wide micro-USDC rounding. The verifier checks the Baby-JubJub successor algebra, private blinding/balance and signature. Only the durable CAS commit makes the successor available. Prior state, proofs and receipts stay in encrypted history.

OA evidence must cover the session expiry with at most the existing issuer adapter's 65-second clock allowance. Expiry is checked again after verifier I/O and before each direct operation. The encrypted journal retains evidence; a fresh SDK instance independently verifies it before sending inference. Only the current instance caches an exact key/evidence/expiry/pin binding. Legacy OA journals without evidence, missing pins and verifier failures cannot authorize inference: the key is discarded and closing is committed before the same session's close request. Close and signed settlement remain available without verifier access. Server-side verification is retained as an additional check; its success is never accepted as the client's verification result. Live OA interoperability still requires the separate provider acceptance gate.

`NativeSessionVerifier` invokes `apps/clientd/companion` through stdin/stdout, with an independently trusted binary SHA-256, no shell or inherited provider environment. The binary and its containing installation directory must be owned and immutable to untrusted processes: a hash check followed by path execution cannot prevent a privileged local replacement race. Symlink executables and group/world-writable binaries are refused. This initial binary accepts the embedded **test request VK only**; production setup requires a corresponding authenticated rebuild.

`EncryptedTransportJournal` implements I04's `Journal.save` and restores exact signed v0 attempts. Financial sends still obey `prepareAttempt`/`recoverAttempt`; buffer absence or expired blockhash never establishes execute failure.

The encryption API takes an application-supplied AES key; `secret-custody.ts` supplies explicit passphrase custody for native hosts that need it. Browser storage requires IndexedDB and Web Locks and fails closed if unavailable. Native locking uses Node's built-in SQLite solely for OS locks; active handles remain rooted until explicit release, including during garbage collection. Records use private files, fsync, rename and directory fsync. A whole-device/whole-directory rollback needs an independently retained trusted head or chain/control reconciliation. A single encrypted backup cannot detect its own rollback. Power-loss durability and other OSes are not established by the local SIGKILL/tab-close tests.

`PROXY_PRIVACY_NOTICE` and `expiryNotice` expose proxy content access, expiry and 7-day/1-day boundaries, including the Active-principal-to-treasury rule. Hosts must present these notices and select direct/proxy explicitly. See `apps/clientd/README.md` for daemon configuration, network routing and packaging. Live provider, external wallet/public RPC and production-release compatibility require their separate gates.

Reproduce the local slice with `python3 scripts/run_i08.py`. It requires Rust, installed SDK dependencies and a Chromium executable (`ZKAPI_TEST_CHROME` can select it), runs real browser storage and native real-proof tests, and rejects skipped tests. Evidence and precise boundaries are in `docs/evidence/I08.md`.

## I08 local proving and wallet workflow

`NoteProver.create(verifiedManifest, detachedArtifacts, engine)` rechecks the authenticated PK/VK/source bytes. The Rust engine in `apps/clientd/prover` generates new original request/withdrawal Groth16 proofs and layout-2 tree transitions, and verifies its proof outputs locally. Request/withdrawal commands hold the private note witness; tree commands receive only public Note/path fields. There is no setup generation, networking, ledger or second client state machine in the prover.

For browsers, bundle `prover-worker.ts` as an isolated module Worker and construct `WorkerProver(worker, wasmBytes, independentlyInstalledWasmSha256)`. WASM obtains randomness from `crypto.getRandomValues`. `ProverSessionVerifier` runs the same Rust preparation/receipt/successor verifier as the native companion, so browser settlement acceptance uses the existing cryptographic checks. Worker failure/timeout/termination can use an explicitly supplied `ClientProver` native fallback; a rejected witness, artifact hash or proof cannot trigger fallback. Call the wrapper's `terminate()` to cancel an in-flight proof. A browser host supplies the authenticated local bridge; Node hosts can directly construct `NativeProver(absoluteExecutablePath, independentlyInstalledSha256)`. Both proof execution paths are offline. Current local verifier builds embed the authenticated **test request VK**; production setup needs an authenticated rebuild.

`WalletClient` uses the same `EncryptedJournal<NoteJournal>` as `ControlClient`. Each note now includes `witness` (secret, note ID, original integer deposit, expiry), private balance/commitment/signature, session history and `wallet` operation/clearance/transaction history. Private fields never enter `SessionCreate`. An old journal containing only `PrivateState` cannot prove a wallet operation; import the separately retained full witness using `importFinalized`, which verifies its private commitment/signature and actual finalized Note account.

Construct `SolanaWalletChain` with a verified manifest, explicit RPC `Connection` and independently configured indexer HTTPS origin. Financial `snapshot` checks RPC genesis, finalized block hashes and a coherent account cut, including actual PoolConfig, TreeState, Note, PendingWithdrawal and Clock layouts/owners. An unchanged root/sequence/next-ID can be authenticated at a newer finalized cut; a changed tree fails closed. Authorization instead uses `sessionSnapshot(noteId, prover)`: common full-snapshot HTTP routes, shared Pool/Tree/Clock RPC reads, and local sparse-path reconstruction in the pinned original-Poseidon prover. It never falls back to selected-note network queries. See [privacy bounds](../../docs/evidence/I10-parity-privacy.md). Use `walletStandardAdapter(wallet, selectedConnectedAccount, chain)` for an explicitly chosen Wallet Standard v0 signer, or supply the same `V0Wallet` interface as I04. Uploader, rent payer, transaction fee payer, instruction payer and deposit token owner are explicit roles.

1. `beginDeposit(id, integerMicroUsdc, roles)` persists a fresh private witness before proving the tree insertion. The note stays `unfunded` until the exact execute receipt is finalized and the corresponding actual Note matches. A stale next ID or Clock/day-boundary expiry regenerates the provisional state with the same secret.
2. `beginWithdrawal(id, 'mutual_close' | 'initiate_escape', destinationOwner, roles)` blocks concurrent control sessions. Mutual close saves the current nullifier intent before clearance HTTP, retries that same nullifier after a lost reply and verifies its Baby-JubJub clearance signature. Clearance remains permanently recorded, preventing another control authorization with that note state. Escape does not require clearance. If clearance is unavailable, explicitly call `fallbackToEscape(id)` before any upload/financial signature exists. It retains the saved destination/roles and permanent nullifier intent, archives the cancelled mutual operation, then proves escape. It never changes mode automatically or replaces a signed attempt.
3. Call `advance(id)` for one sign/recover step. Every exact signed v0 attempt is encrypted and committed before sending. An unknown execute/close/finalize can only query or resend that same signature; expired blockhash or missing accounts cannot create a replacement. The existing I04 upload reconciliation handles eligible expired append/seal attempts.
4. `proof_required` calls for `resumeProof(id)`. After a finalized stale rejection, the workflow first closes the old buffer and finalizes that receipt, then generates a fresh payload/buffer using the current root/path. Close/escape regenerate both withdrawal and tree proofs while retaining the same nullifier/clearance. Wallet rejection or process restart leaves the saved operation available for explicit continuation.
5. After escape finalizes, the journal becomes `pending_escape`. `beginFinalize(id, roles)` verifies the actual pending destination/nullifier and challenge deadline, then prepares the existing no-proof finalize path. `advance` activates the terminal state only after the finalized receipt and actual account check.
6. A non-stale finalized rejection leaves the operation `failed`. After addressing its cause, explicitly call `retryRejected(id)`. It re-verifies the exact rejected signature and checks the old buffer at or after that receipt slot, then closes an existing buffer before fresh proving. A finalized absent buffer permits proving directly. Deposit retries preserve the secret and recheck the current next ID/expiry; withdrawal retries preserve the destination, nullifier and clearance. Finalize retries recheck the saved Pending identity/balance and deadline. Missing receipts, uncertain sends and blockhash expiry cannot authorize this retry.

Run `python3 scripts/run_i08_wallet.py` with the repository's pinned Node/npm, Rust WASM target, GNU tar and Chromium. `ZKAPI_NPM_CLI` can select an installed npm CLI when the pinned Node archive bundles another npm version. Prerequisites are I04's actual Vault SBF ELF, I05's generated manifest and I09's pinned public test tree setup. The runner rebuilds native/WASM, generates real proofs in Chromium, runs those new proof bytes through SDK-signed v0 buffers in actual Vault SBF, and tests the complete durable wallet workflow including stale root/expiry, wallet rejection, lost sends, clearance and escape/finalize. It rejects skips and writes commands, versions, hashes, timings and CU/transaction limits to `target/i08-wallet/runtime-report.json`. RPC finality and clearance HTTP are local fixtures; no public RPC, browser-extension wallet, provider or release gate is claimed.
