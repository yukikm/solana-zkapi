# I06 — OA-org / OpenRouter direct adapters

2026-10-04 JST。I05共有台帳へdirect provider HTTP adapterと復旧処理を接続した。**direct adapter単体は初回local 10テスト、レビュー後12テスト成功。実provider権限・G3は未検証**。実provider credentialの発行、購入、live推論は今回行っていない。

## 実装

- `services/control/src/direct/`：OA-org発行・固定verifier検証・管理参照回収・最終usage、OpenRouter発行・list回収・disable・usage・delete。
- `DirectRuntime`：I05のimmutable attempt→最終claim→一回発行を使用。発行HTTPを再送しない。未確定発行は`ISSUANCE_UNKNOWN`、再開時は元requestの管理情報だけを照会し、key再配信・proxyへの切替をしない。
- 管理参照を検証者/最終chain照会より前に共有ledger checkpointへ保存。遅延成功・verifier拒否・close/chain exitはDRAININGへ進める。checkpointは専用outboxイベントとしてwriter接続で追記し、CAS・不変のintent/管理参照・厳密な構造を検証する。runtime key、provider応答本文、管理credentialはcheckpointへ保存しない。
- OpenRouterではdisable確認後の設定graceを待ってusageを読み、さらにgraceを隔てた同じ正規化USDの観測を要求する。増加は観測を更新して待機し、減少は拒否。最終USD・証拠digestを**DELETEより前**に永続化し、DELETE応答喪失後も既存値で復旧する。404はこの保存済みusageを持つ削除再試行でだけ削除完了として利用する。
- 上流JSONのUSDは`RawValue`のnumber lexemeを取り出して任意精度整数で合算。`usage + byok_usage`を合計してからnano切上げし、cap超過分は運営損失。0 usageと欠落usageを区別する。
- OpenRouter URLは`https://openrouter.ai/api/v1`に固定。OA issuer/verifier/station/inferenceは運営設定へpinし、応答URLで転送先を決めない。HTTPS必須、explicit local testだけnumeric loopback HTTPを許可。redirect、自動HTTP retry、環境proxyを無効化し、HTTP応答を1 MiB/35秒で制限。エラーにprovider本文・secretを含めない。

## 元実装と意図した差分

基準は`ethereum/zkapi@045b444ea1b52538d1b40273c7cb6ed09468a052`、元licenseを保持する。OAの`request_key`/`reconcile_key`/`key_usage`とstation request IDのSHA256式、browser SDKの固定verifier `/submit_key`（`status=verified`）を移植した。`station_recently_attested`だけで鍵を認証しない。verifier停止時の未検証鍵fallbackは提供しない。

元OA serverはusage receiptのfield・lease bindingと128桁hex署名形式を検査しており、**receiptのEd25519署名を公開鍵から独立に再検証するpayload契約は固定repoに存在しない**。今回も固定issuerの認証transportから取得したsigned receiptの構造・request/lease bindingを検査する。`OA_SIGNED_RECEIPT`は証拠の出所区分であり、独立した暗号検証済みprovider usageという主張ではない。fixtureの署名は合成である。実issuerの公開鍵/署名payload・verifier/usageの受入証拠はG3で別途確認する。

OA `key_usage`の`pending`は精算を保留し、`finalized`は元stationが停止・集計・永続receipt・削除を担当する契約として扱う。制御serverからstation管理credentialを使って別のdisable/deleteを呼ぶ架空APIは追加しない。

元OpenRouter adapterのbinary floatを廃止し、USD lexemeと1 USD = 1 USDCの整数精算へ変更した。上流のusageの確定時刻を証明するAPIはない。二回の安定観測とgraceは運用上の判定であり、provider請求の確定証明ではない。この意味でOAとOpenRouterの証拠区分を混同しない。

発行失敗時の一般HTTP statusや空listから「未発行」を推測しない。これは元の限定policy rejection最適化より保守的であり、曖昧な発行の無料精算・再発行を防ぐ。DB上のattempt未claimで送信が無かった場合だけ、共有ledgerの既存未発行経路を使用できる。旧processの送信能力が不明なままDBフラグでfenceしたとは扱わない。

### 制御HTTPの配信中断・同時作成回帰

`services/control/tests/provider_http_runtime.rs`を実PostgreSQL・実request proof・別process signerで実行し、**4件成功・0失敗・0除外**（11.00秒）を確認した。directの初回keyのみ配信、usage保存後のDELETE応答喪失、proxyのSSE切断後usage/unknown waiverに加え、次の配信境界を検証した。

- `unconsumed_direct_response_body_closes_and_settles_without_key_replay`：`app.router().oneshot`で初回201応答を得た直後、bodyを一度もpollせず破棄。response bodyのguardが`close_requested`を永続化することを待って確認し、明示closeを追加せず通常復旧でSETTLEDまで進めた。同一認可の再送は後継状態だけを返し、key再配信・再発行・重複明細がない。
- `concurrent_direct_creation_issues_once_without_closing_live_session`：同一request/proof/credentialの初回POSTを並行実行。上流発行は1回、keyを含む応答は1件、両HTTP応答は200または201。重複側の処理が元のACTIVE sessionを閉じず、close後の精算明細も1件であることを確認した。

```sh

  --test provider_http_runtime -- --include-ignored --nocapture --test-threads=1
```

## 2026-10-04 レビュー修正とI08/I09への引き継ぎ

未コミットのI06/I07実装を仕様・固定upstream・HTTP/DB/process境界から再レビューした。I06と共通runtimeでは次の4件を修正した。元回路・Vault・整数会計・独立signer journalを置き換えていない。

| 問題 | 修正と回帰 |
|---|---|
| OA発行済みkeyの`credit_limit`が不正だと既知の管理参照も破棄 | 配信拒否と管理参照保持を分離。文字列/負数/nullの3例で、verifierへ送らず最終usageの取得まで可能なことを`oa_malformed_limit_retains_management_reference_for_retirement`で確認 |
| provider Mutex待ち前の時刻で短期leaseを計算し、実送信時には期限切れ | Mutex取得と既存checkpoint確認後に、初回だけ発行時刻を固定。RP/quoteは不変。古いintentから未来expiryを持つ発行を行い、再呼出し・reconcileで保存済みintent/referenceを変更しないことを`direct_issuance_starts_lease_after_wait_and_preserves_recovery_intent`で確認 |
| 発行結果がoneshot内にある間のhandler取消しでkeyが失われclose未保存 | 発行taskで`DirectDelivery` guardを生成し、keyと一緒にchannelへ移す。`queued_direct_key_is_retired_when_creation_handler_is_abandoned`でhandlerを意図的に未pollのまま破棄し、close→SETTLED・発行/明細各1件を確認。keyを持たないduplicateの送信失敗では元sessionを閉じない |
| 新writerが旧epochのattemptをinventoryから取得して`finish_attempt`できる | 現writer epochとの一致を強制。旧direct/proxy attemptのfinishと再claimを拒否し、quiescedにならないことを`provider_ledger`のrestart回帰で確認。解除は実停止に基づくfencingが必要 |
