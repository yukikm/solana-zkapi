## 独立signerと復旧の実証

signer RPCはsettlementのrequest ID、clearanceのN、reconcileだけを受け付ける。任意messageを渡すendpointはない。role別秘密鍵から導出した公開鍵、build pin、trusted config、primaryの固定pool設定が一致しなければ起動/署名を拒否する。quote/receiptは別Ed25519鍵を使う。

signerはread-only primary snapshotでschema version/checksum、実RP・Authorization/quote結合、凍結tariff・署名receiptの再計算、予約0、全operation終端、全attempt終了/fencingを確認する。`server_update` と保存済みanchor乱数から後継commitment/anchor/messageを再導出する。journalはpool/Nを永久キーとしてrole・request ID・公開鍵・message・対象digestをpinし、署名**前**にfsyncする。生成署名もfsyncしてから返し、writerが検証・DB保存して初めて公開する。

| 停止対象・地点 | 永続状態と確認 |
|---|---|
| controld：`reserved` | 認可commit後のRESERVEDでexit 86。再起動して同じ認可を回復し、closeで0課金後継を一つだけ公開 |
| controld：`sign_pending` | 後継charge/anchor/delta/乱数/message保存後のSIGN_PENDINGでexit 86。再起動で同一対象を署名 |
| controld：`signature` | signer署名取得後・ledger保存前にexit 86。journalの署名を回収し保存、乱数を再生成しない |
| controld：`settled` | ledger署名保存後・HTTP完了前にexit 86。再起動後のPOST/status/closeが同じSETTLED結果を返す |
| signerd：`intent` | 署名前のintent fsync後にexit 86。同一messageだけ再開 |
| signerd：`signature` | 実署名生成後・署名journal保存前にexit 86。未署名intentが拘束する同一messageだけ再署名可能 |
| signerd：`synced` | 署名fsync後・返却前にexit 86。保存済み署名bytesを同一のまま再返却 |
| signerd：primary保存後 | 子processを実killしてwait、再起動。同一journal署名とprimary署名が一致 |
| writer DB connection | `pg_terminate_backend`でlock所有connectionを終了。旧writerは新規書込み不可、後継writerはepochを上げて受付停止状態から開始 |

`exit(86)`はdestructorを実行しない明示的fault hookであり、すべてをOS SIGKILLや電源断試験とは呼ばない。local owner停止とsignerの保存後再起動は実child kill/waitを使用した。ledgerだけのrestore相当試験ではmigration権限で対象行を欠落/改変させ、独立journalとの不一致が無関係な新規署名まで止めることを確認。署名済みledgerに対する空journal、missing journal、破損/途中journalも拒否する。物理backup restore、WAL/LSN同期、host損失・disk故障・本番egress遮断・RPO/RTOは検証していない。

## 実cryptoからUSDC残高まで

1. I04の実Vault ELFをLiteSVMへロードし、実PDA/ATA/CPIとv0 bufferで5,000,000 microを入金。PoolConfig/TreeState/ExitNullifierの実bytesをexportする。
2. HTTPでEd25519 quoteを発行し、固定upstream proving keyでAuthorizationを結合した実RPを生成・受理する。
3. local usageを凍結有理数料金で1,001 nanoに確定し、unknownと未送信の0課金明細も含めて署名・合算する。sessionの切上げは一回だけで2 micro。
4. 別process signerがprimaryを独立照合し、新しいBaby-JubJub state署名をjournal保存。writerが検証・保存する。signer再起動後も同じ署名が返る。
5. 利用者残高4,999,998、旧blind＋rerandomization＋保存delta、新anchor、新state署名から**次の実RP**を生成・検証。次Nに独立clearance署名を発行し、それを含む**新しい実WP**を生成・検証する。
6. そのWPと、同じNote/root/遷移に対応する**既存の実tree proof**をv0 bufferへuploadし、実Vault closeを実行。新しいsigner署名は既存I03固定署名fixtureで代用していない。tree回路・hashの変更やtree proof再生成を今回の成果としては主張しない。

この実SBF試験はlocal 6-decimal SPL tokenと公開test entropyを使う。Circleのlive USDC mint、実walletや公開clusterへの送信ではない。既存I03/I04全回帰を今回もう一度実行したとは主張せず、再利用ELFと今回の10取引を別に記録する。

## 限界・次工程

schema検査は適用SQLのversion/checksumとruntime role権限の検証であり、特権DBAによる任意のphysical schema書換えや全backup整合性の証明ではない。signerはprimary targetの意味と独立journalを追加照合する。秘密ファイル・journalはowner-onlyで、現在のDB接続はlocal `NoTls`、signer RPCはprivate Unix socket。production KMS envelope、mTLS、swap/core-dump運用、remote storage、複数hostのfailover/egress fencingは後続である。

I04 indexerのready HTTP contractを利用したが、I05試験のroot応答・slot/finality・RPC障害はlocal fixture。indexer archive replay全体をこのI05 suiteが再実証したものではない。root鮮度・片側exit拒否のlocal確認を公開cluster上の競合解消保証とはしない。

privacy検査は保存経路の型制約、local token/canaryのDB dump・journal・log不在assertまで。実providerを使ったprompt/応答/鍵・trace・本番backup全体の漏えい検査と、provider固有usageの外部照合は後続に残る。集計未知のproxy操作を推測課金しない一方、directではkey停止・最終usage確定を省略して無料精算しない。
