# I03 — Anchor Vault / USDC

2026-10-03 JST。**I03完了、次はI04**。I02-Bの`2988e5e`を基準に、layout 2 / transition_proof / proof_boundのVaultを実装した。実SBF 366取引と固定Ethereum版との比較を確認。production setup、実Circle USDC送金、I04全buffer lifecycle、G1〜G4の完了は主張しない。

## 成果物

- [Vault](../../programs/zkapi-vault/src/lib.rs)：initialize、deposit、mutual close、escape、challenge、finalize、expiry、treasury変更、pause/unpause。厳密な命令長を検査するSBF入口と、署名付きsealed bufferのexecuteも実装。
- [共通handler](../../programs/zkapi-vault/src/handlers.rs)：Pool/Tree/Note/Pending/ExitのPDAとlayout、固定mint/Token Program、正規ATA/authority、profile、整数会計を検査する。I02-Bのcodec/bindingと固定VKを再利用する。
- [Account/event定義](../../programs/zkapi-vault/src/state.rs)：Closed NoteとExitNullifierを永続保存し、challenge後もNを再利用させない。全資金遷移のsequence、outstanding deposits、VaultTransitionV1を記録する。
- [実SBF試験](../../tests/svm/src/bin/vault.rs)と[実proof fixture生成器](../../crates/zkapi-tree-prover/examples/vault_fixtures.rs)：program ID/PDAに結合した元request/withdrawal証明と追加tree証明を使用。native processorによる代替ではない。
- [固定Ethereum実装との比較](../../tests/evm-vault/README.md)：同じ整数D/B/id/時刻/操作列のroot、leaf、Note、Pending、N、利用者/treasury残高と拒否条件を比較する。
- [IDL生成器](../../tools/vault-idl/src/main.rs)：Anchorのcompiler-backed IDLと実Account型のIdlBuildを使う。手書きのschemaを正本にしない。

## 実行結果

[全SBFケース・CU・ログ・ELF hash](I03-svm-results.json)：366取引、203成功・163拒否、184種類のcase label（初期化等のsetupを繰り返す）。全取引がComputeBudget 1,000,000 CU、ALTなしの署名付きv0で1232 bytes以下。測定最大426,765 CU、863 bytes。予算引上げやnative processorを使ってVault試験を合格させていない。

これらは試験したaccount/分岐の実測値で、I04のupload工程・wallet・target clusterのworst-case gateを代替しない。固定LiteSVM/Agaveとbundled SPL Token SBFで測定したローカル結果である。

- 正常系：全資金遷移、署名済み後継とgenesis全額出金、expiry後の合意出金、pause中のchallenge/finalize/expiry、既存Pendingへのtreasury変更、payerとtoken ownerの分離、prefunded PDAのallocate/assign。
- 暗号：TP全11 inputs、WP全14、RP全12、proof座標8、別Note/Vault/rootの有効proof混合、過去RP.rootの維持、別compile VKのtree/withdrawal/request拒否。
- 状態：PDA/owner/layout/profile、固定mint/Token Program/ATA/authority/delegate、N tombstone、最大u32 IDとTreeFull sentinel、timestamp/TTL/challenge/sequence/outstanding/token残高overflow、pauseとdeadline等号。
- rollback：closeとfinalizeの1回目TransferChecked成功ログの後、2回目treasury転送を凍結エラー17で失敗させた。全program/token account bytes・lamports・作成予定ATAの不在・buffer保持を比較した。失敗transactionにもログは残るため、indexerはmeta.errを確認する。
- event：全fieldとOption値をNote/Pendingの実状態と照合し、finalizeのroot不変・sequence増加も検査。rentは保存済みpayerへ正確に返却。

[Ethereum比較](I03-parity.json)：固定元Vault、元VKの実proofで11テスト成功。7シナリオ・27状態・13項目・14拒否条件がSolana側と一致した。資産単位/H2F/u64 counter/tree proof/初期化条件の差分はレポートに明記。provider利用の代替ではなく、非genesis署名済み残高を使う回路経路の比較である。

[生成IDL](../contracts/zkapi_vault.json)は11命令（10規範命令＋execute）、6 account型、VaultTransitionV1、固定エラー6000–6018を含む。wire長/discriminator/field順を[IDL検査](../../scripts/check_vault_idl.py)で照合した。Anchorのsource-parser lintは外部`#[path]`参照を解決できないためIDL生成時だけ無効化し、Rustコンパイルと実SBF account拒否試験を実行した。Anchor IDL builderは0.1.4へ固定している。

## I04との境界

I03試験はsealed PayloadBufferだけをLiteSVMへ事前投入し、Pool/Tree/Note/Pending/Exit/ATAの生成、実proof検証、Token CPI、イベント、buffer rent返却を実行する。create/append/seal/close、wallet、blockhash切れ/復旧、indexerはI04に残る。事前投入したbufferでのexecute成功をアップロード工程の完了と数えない。

PoolConfigにはpool_id、PayloadBufferにはnonceを保存して各呼出しでseedを検証する。nonceはpayloadの後ろに保存する。共通Financial contextの未使用accountにもwritable条件があるため、未使用placeholderにはpayerを指定し、実行可能program accountをwritable placeholderにしない。depositのinline IDLはtoken ownerの署名を明示し、buffer経路でも同じ署名条件を検査する。

test buildのmintはローカル6-decimal SPL fixture。devnet featureは公開devnet mintを固定し、本番USDCの転送実績とは区別する。request/withdrawal/treeのsetup、署名鍵、deployment authorityはテスト用で、provider/API/DB処理を実施した証拠ではない。
